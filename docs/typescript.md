# TypeScript

`tug gen` writes the TypeScript of an app's Go types: the props each page
takes, the props every page shares, and the named routes. The TypeScript
compiler then checks a page component against the handler that renders it,
as Go's compiler checks the handler.

## What you get

Two files, in `resources/js/tug`:

- `pages.ts`: an interface for each Go struct the props use, `SharedProps`,
  `Pages`, and `PageProps<'Component'>`, which is a page's own props and
  the shared ones.
- `routes.ts`: the named routes, the values each one's path needs, and
  `route()`, which builds a route's path as `App.URL` does in Go.

Both start with the line
`// Code generated by tug gen from the Go types. DO NOT EDIT.`: tug writes
them again whenever the Go changes, and an edit made by hand is lost at
the next write.

A page and two routes, in Go:

```go
type Post struct {
	ID    int64    `json:"id"`
	Title string   `json:"title"`
	Body  string   `json:"body"`
	Tags  []string `json:"tags"`
}

type PostsShowProps struct {
	Post Post `json:"post"`
}

var PostsShow = tug.Page[PostsShowProps]("Posts/Show")

// in main, with the other routes
app.Get("/posts/{id}", show).Name("posts.show")
app.Get("/posts/{id}/edit", edit).Name("posts.edit")
```

`pages.ts` gets `Post` and `PostsShowProps` as interfaces, and
`'Posts/Show': PostsShowProps` in `Pages`. `routes.ts` gets `'posts.edit'`,
whose path needs `{ id: string | number }`. The component takes them:

```tsx
import { Link } from '@inertiajs/react'
import type { PageProps } from '../../tug/pages'
import { route } from '../../tug/routes'

export default function Show({ post, appName }: PageProps<'Posts/Show'>) {
  return (
    <article>
      <h1>{post.title}</h1>
      <p>{post.body}</p>
      <Link href={route('posts.edit', { id: post.id })}>Edit</Link>
      <footer>{appName}</footer>
    </article>
  )
}
```

`appName` is a shared prop, from `pages.Share("appName", "blog")`. Each of
these doesn't compile:

- `post.titel`: "Property 'titel' does not exist on type 'Post'. Did you
  mean 'title'?"
- `PageProps<'Posts/Shwo'>`: no `tug.Page` declared that component, so it
  isn't in `keyof Pages`.
- `route('post.edit', { id: post.id })`: no route has that name.
- `route('posts.edit')`: "Expected 2 arguments, but got 1." The path needs
  its `{id}`; given `{}`, the error names the missing `id`.
- `route('posts.edit', { slug: 'hello' })`: the path has no `{slug}`. A
  value for a wildcard the path doesn't have is refused even next to the
  ones it needs, and a path with no wildcards takes no values at all.

When a Go field is renamed, removed or given another type, the next
`tug gen` changes its interface, and every component that uses the old
field stops compiling. `tug build` type-checks before it builds, with the
app's `typecheck` script (`tsc --noEmit` in the starters); Vite's build
alone doesn't check types.

## How tug gen learns the app

`tug gen` builds the app into `.tug/app` and runs it with `TUG_GEN` set to
a file. `App.Run` looks for `TUG_GEN` before anything else. When it's set,
`Run` writes the app's TypeScript to that file and returns without
listening. tug gen then writes the two files, each only when it has
changed, so that an unchanged file doesn't set off Vite or an editor. It
says which it wrote, as `wrote resources/js/tug/pages.ts`, or "the types
are up to date".

tug gen runs the app rather than read its source because route groups and
their prefixes only exist once the app runs. So the TypeScript is of what
`main` has set up by the time it calls `Run`:

- **Pages**: the ones `tug.Page` declared. It records each component and
  its props type when it's called, which for a package-level `var` is
  before `main` starts. `Config.ErrorPage` is there too, with
  `ErrorPageProps`: `{ status: number; message: string }`. A page rendered
  with `c.Inertia("Name", props)`, and never declared, isn't.
- **Shared props**: the values given to `Share`, by their Go type. Props
  that `ShareFunc` or `inertia.WithProps` add per request aren't; see
  [Shared props](#shared-props).
- **Routes**: the ones named with `.Name`, with their method and whole
  path, group prefixes included.

The TypeScript is written inside the app, by the tug that its go.mod
requires. The CLI builds the app, runs it, and puts the files in place.

Whatever `main` does before `Run`, it does for tug gen too. It runs with
the environment tug has, and the app's `.env` under it, as `tug dev` reads
it. Both starters stop without an `APP_KEY`, and tug gen shows why:

```
tug: the app stopped before writing its types (exit status 1):
2026/09/25 15:56:12 session: APP_KEY isn't set; make one with `head -c 32 /dev/urandom | base64` and set APP_KEY=base64:<that>
```

The auth starter also opens its SQLite database, making `app.db` when
there isn't one, and stops without `APP_URL` unless `APP_DEBUG` is on. A
`main` that doesn't call `Run` writes no types, and tug gen asks "does main
call app.Run?": at once when the app exits, and after 30 seconds when it
keeps running.

## From Go to TypeScript

The types say what encoding/json writes:

```go
type Timestamps struct {
	CreatedAt time.Time  `json:"createdAt"`
	UpdatedAt *time.Time `json:"updatedAt"`
}

type Post struct {
	Timestamps
	ID     int64          `json:"id"`
	Title  string         `json:"title"`
	Draft  bool           `json:"draft,omitempty"`
	Tags   []string       `json:"tags"`
	Author *User          `json:"author"`
	Meta   map[string]any `json:"meta"`
	secret string
}

type PostsIndexProps struct {
	Posts inertia.ScrollProp[Post]       `json:"posts"`
	Stats inertia.DeferProp[Stats]       `json:"stats"`
	Tags  inertia.OptionalProp[[]string] `json:"tags"`
}
```

```ts
export interface Post {
  createdAt: string
  updatedAt: string | null
  id: number
  title: string
  draft?: boolean
  tags: string[]
  author: User | null
  meta: Record<string, unknown>
}

export interface PostsIndexProps {
  posts: { data: Post[] }
  stats?: Stats
  tags?: string[]
}
```

| Go                                             | TypeScript |
|------------------------------------------------|------------|
| `bool`                                         | `boolean` |
| `int`, `uint8`, `float64`, and the other numbers | `number` |
| `string`                                       | `string` |
| `[]byte`                                       | `string`, the base64 that encoding/json writes; a `[N]byte` is `number[]` |
| `[]T`, `[N]T`                                  | `T[]`, or `(A \| B)[]` for a union: `[]*int` is `(number \| null)[]` |
| `map[K]V`                                      | `Record<string, V>`: a JSON object's keys are strings |
| `*T`                                           | `T \| null` |
| a named struct, `Post`                         | `Post`, an interface of its own |
| a generic struct, `List[Post]`                 | `List_Post`, an interface of its own |
| an anonymous struct                            | the object type, on one line: `{ lat: number; lng: number }` |
| `time.Time`                                    | `string` |
| `json.RawMessage`, and a type with a `MarshalJSON` method | `unknown` |
| a type with a `MarshalText` method, such as `netip.Addr` | `string` |
| an interface, such as `any` or `error`         | `unknown` |

A struct's fields:

- A field is named by its json tag, or by its Go name when it has none.
- Unexported fields, and fields tagged `json:"-"`, are left out.
- `omitempty` or `omitzero` makes the property optional: `draft?: boolean`.
- `,string` makes it a `string`, as encoding/json quotes the value.
- An embedded struct with no json name has its fields promoted into the
  struct's own, as `Timestamps` above; with a name, it's a property.
- A name that isn't a JavaScript identifier is quoted: `'user-count': number`.

Package `inertia`'s prop types go out as the value they hold, so their type
is that value's:

| Go                                                     | TypeScript |
|--------------------------------------------------------|------------|
| `inertia.DeferProp[T]`, `inertia.OptionalProp[T]`      | `T`, and the property is optional: `stats?: Stats` |
| `inertia.LazyProp[T]`, `AlwaysProp[T]`, `MergeProp[T]`, `OnceProp[T]` | `T` |
| `inertia.ScrollProp[T]`                                | `{ data: T[] }` |

A deferred prop is left out of the first load, and an optional one until a
partial reload asks for it, so a page checks it's there before using it:
`{stats && <StatsLine stats={stats} />}`. `Defer(fn).Merge()` and
`.Rescue()` still make a `DeferProp`, so they're optional too.
`Scroll(fn).Defer()` is still a `ScrollProp`, whose type says nothing of
the `Defer`, so its property isn't marked optional, though the first load
leaves it out: read it inside `<Deferred data="posts">`, which shows its
children once the prop is there.

Each named struct is one interface, named after its Go type and declared
once however often it's used. Interfaces are listed by name. When two
packages have types of the same name, the one met first keeps the name and
the other has its package's name in front: `Decoder` from encoding/json
beside `xml_Decoder`.

A page's props are its props struct's interface. A page whose props type
isn't a struct, such as `tug.Page[tug.Props]`, has
`Record<string, unknown>`, and one with `struct{}` has `{}`.

## Shared props

`SharedProps` has a property for each value given to `Share`:

```go
pages.Share("appName", "blog")
```

```ts
export interface SharedProps {
  appName: string
}
```

`PageProps<C>` is `Pages[C] & SharedProps`. `pages.ts` also tells
Inertia's own types about them, by adding `sharedPageProps: SharedProps`
to the `InertiaConfig` interface of `@inertiajs/core`. So `usePage()` knows
the shared props with no type argument, as the starter's `Layout.tsx` uses
it:

```tsx
const { props, flash } = usePage()
// props.appName is a string
```

A page's own props aren't in `usePage()`'s type: they come to the page
component. The generated interfaces don't fit `usePage`'s type parameter,
which asks for an index signature, so `usePage<PageProps<'Posts/Show'>>()`
doesn't compile. Pass a child the props it needs.

A prop that `ShareFunc` works out for each request has no type tug gen can
see. Give `Share` a first value of the same type, and tug gen learns the
type from it; when a page is rendered, `ShareFunc`'s value takes its place.
The auth starter shares the user this way:

```go
// Auth is the auth prop every page shares: the user who's logged in, or
// null for a guest.
type Auth struct {
	User *User `json:"user"`
}

pages.Share("auth", Auth{})
pages.ShareFunc(a.shareAuth) // inertia.Props{"auth": Auth{User: u}}
```

`SharedProps` gets `auth: Auth`, and `pages.ts` an interface
`Auth { user: User | null }`, so every page has `auth.user` typed.

For a prop with no first value to give, or one that middleware adds with
`inertia.WithProps`, add it to `SharedProps` from a file of your own. The
path in `declare module` is relative to that file. `resources/js/types.ts`,
where the starters keep the flash type, will do:

```ts
declare module './tug/pages' {
  interface SharedProps {
    unread: number
  }
}
```

The file ends in `export {}`, which makes it a module: outside one,
TypeScript refuses a relative path in `declare module`.

Flash data isn't a prop, and `c.Flash` takes any key, so tug gen doesn't
write its type. It's in `resources/js/types.ts`, which the starters come
with:

```ts
// What the handlers flash with c.Flash, for usePage().flash. The props of
// the pages, and the routes, are in ./tug, written by tug gen.
declare module '@inertiajs/core' {
  export interface InertiaConfig {
    flashDataType: { success?: string }
  }
}

export {}
```

With it, `usePage().flash.success` is a `string | undefined`, and
`flash.error` doesn't compile until the type has it. Keep it in step with
what the handlers flash; [forms.md](forms.md) has flash data itself.

## Routes

```ts
export const routes = {
  'files': { method: 'get', path: '/files/{path...}' },
  'posts.destroy': { method: 'delete', path: '/posts/{id}' },
  'posts.index': { method: 'get', path: '/{$}' },
  'posts.show': { method: 'get', path: '/posts/{id}' },
} as const

export interface Params {
  'files': { path: string | number }
  'posts.destroy': { id: string | number }
  'posts.index': Record<string, never>
  'posts.show': { id: string | number }
}

export type RouteName = keyof Params
```

- `routes` has each named route's method, in lower case, and its path as
  ServeMux has it: with its group's prefix, and with the `{$}` that tug
  adds to a path ending in `/`. A route for any method, from `Any`, is
  listed as `'get'`.
- `Params` has a value for each wildcard, a string or a number, and
  `Record<string, never>` for a route without one.
- `RouteName` is any of the names. A route without a name isn't here:
  name it to use it from the frontend.

`route(name, params)` builds the path. It needs `params` when the path has
wildcards, and takes none when it hasn't:

```ts
route('posts.show', { id: 42 })                         // '/posts/42'
route('posts.index')                                    // '/'
route('files', { path: 'reports/2026/q3 summary.pdf' }) // '/files/reports/2026/q3%20summary.pdf'
```

A `{id}` wildcard gets its value escaped whole, so a `/` in it becomes
`%2F`. A `{path...}` wildcard gets its value escaped between the slashes,
which stay. `{$}` is replaced with nothing, which leaves the `/` before it.
Like `App.URL`, `route()` returns a path, not a whole URL. A route's method
is for the component to say, as a link that deletes does:

```tsx
<Link href={route('posts.destroy', { id: post.id })} method="delete" as="button">
  Delete
</Link>
```

## Keeping them current

`tug new` writes the types. `tug dev` writes them again after each rebuild,
which a change to a Go file, go.mod or a template starts. `tug build`
writes them first, then type-checks and builds the frontend. After
changing Go types without `tug dev` running, run `tug gen`.

Commit the two files. `routes.ts` is code the pages import, and the
Dockerfile's frontend stage builds from the files as they are: it has Node
but no Go, so it can't write them.

CI can check that they match the Go, as this repository's workflow does
for `examples/inertia`. It runs tug gen, then
`git diff --exit-code resources/js/tug`, which fails when tug gen has
changed the files: when the Go changed, and the types written from it
weren't committed.

In an app's own CI, `go run github.com/cuonggt/tug/cmd/tug` runs the CLI
of the tug that go.mod requires, with nothing to install. The app runs as
`main` has it, so give it what it needs to reach `Run`. Any key will do,
as it serves nothing; the auth starter also needs `APP_DEBUG` on, or an
`APP_URL`:

```yaml
- run: npm ci
- name: the types are the Go ones
  run: |
    export APP_KEY=base64:$(head -c 32 /dev/urandom | base64) APP_DEBUG=true
    go run github.com/cuonggt/tug/cmd/tug gen
    git diff --exit-code resources/js/tug
- run: npm run typecheck
```
